# StartupHub — AI-Powered Startup Business Planning Platform

Turn a raw business idea, a budget, and a target customer into a
structured, practical business plan — generated by AI, validated on the
backend, and saved to your account.

## 1. Project overview

StartupHub is a full-stack MERN application. A user registers, describes
a business idea (idea, budget, target customers, plus optional context),
and the backend calls an AI provider to generate a structured business
plan covering everything from an executive summary to a 30/60/90-day
action plan. The user can save, edit, duplicate, regenerate, copy, or
download the plan as a PDF, all from a dashboard that reflects real data
from MongoDB.

## 2. Features

- Secure registration/login (JWT + bcrypt password hashing)
- Protected dashboard and API routes; plans are strictly per-user
- Business plan form: business idea, budget, target customers (required)
  + industry, location, business type, timeline, experience level, goals,
  revenue model preference (optional)
- AI-generated structured business plan (26-section schema — see below)
- Save / View / Edit / Delete / Duplicate / Regenerate / Download PDF / Copy
- Dashboard with real statistics (total plans, plans this month, average
  budget, latest plan) and charts (plans over time, budget distribution)
- My Plans page with search, sort, and empty states
- Toast notifications, loading states, and friendly error states throughout
- Profile page (update name) and Settings page (theme preference)
- Fully responsive (320px through desktop)
- Clear "AI not configured" messaging when no `AI_API_KEY` is set — never
  fake AI output

## 3. Tech stack

**Frontend:** React 18 (Vite) · React Router · Tailwind CSS · Axios ·
Recharts · lucide-react · jsPDF

**Backend:** Node.js · Express · MongoDB (Mongoose) · JWT · bcryptjs ·
express-validator · Helmet · express-rate-limit · dotenv · cors · morgan

**AI:** Any OpenAI-compatible `/chat/completions` provider, fully
configurable via `AI_PROVIDER` / `AI_MODEL` / `AI_API_KEY` / `AI_API_BASE_URL`

## 8. Environment variables

Copy the example files and fill them in:

```bash
cp server/.env.example server/.env
cp client/.env.example client/.env
```

**`server/.env`**
```
PORT=5000
MONGODB_URI=your-mongodb-connection-string
JWT_SECRET=a-long-random-string
AI_API_KEY=your-ai-provider-key      # optional — see section 10
AI_MODEL=gpt-4o-mini
AI_PROVIDER=openai
CLIENT_URL=http://localhost:5173
```

**`client/.env`**
```
VITE_API_URL=http://localhost:5000/api
```

Never commit real secrets — only the `.env.example` files are checked in.

## 9. MongoDB setup

- **Local:** install MongoDB Community Edition, run `mongod`, and use
  `MONGODB_URI=mongodb://127.0.0.1:27017/startuphub`.
- **Atlas (recommended for quick setup):** create a free cluster at
  mongodb.com/atlas, add a database user, allow your IP (or `0.0.0.0/0`
  for local testing), and copy the provided connection string into
  `MONGODB_URI`.

## 10. AI API setup

StartupHub calls a standard OpenAI-compatible `/chat/completions`
endpoint. To enable real generation:

1. Get an API key from your chosen provider.
2. Set `AI_API_KEY` in `server/.env`.
3. (Optional) Set `AI_MODEL` and `AI_API_BASE_URL` if you're not using
   OpenAI directly — any provider exposing the same endpoint shape works
   without code changes.

**Without an `AI_API_KEY`:** the app does not fake AI output. Every AI
endpoint responds with `{ aiConfigured: false, message: "..." }`, and the
frontend shows a clear "AI generation is not configured yet" notice
instead of pretending to generate a plan.

## 14. Authentication flow

Register/login return a JWT, stored in `localStorage` on the client and
attached as `Authorization: Bearer <token>` on every subsequent request
(via an Axios interceptor). The backend's `protect` middleware verifies
the token and re-fetches the user on every request, so a deleted user's
token stops working immediately. A `401` response anywhere clears the
stored token/user, and `ProtectedRoute` redirects to `/login`.

**Token storage tradeoff:** for simplicity (and because this is a
single-origin local/college deployment), the JWT is kept in
`localStorage` rather than an HTTP-only cookie. This is simple and works
well here, but is vulnerable to token theft via XSS in a production
setting with untrusted third-party scripts. A production hardening step
would be to switch to an HTTP-only, `Secure`, `SameSite=Strict` cookie
issued by the backend instead.

## 15. Database structure

**User**: `name`, `email` (unique), `password` (hashed, never returned),
`theme`, timestamps.

**BusinessPlan**: `userId` (ref User, indexed), `title`, `businessIdea`,
`budget`, `targetCustomers`, `industry`, `location`, `businessType`,
`timeline`, `experienceLevel`, `goals`, `revenueModelPreference`,
`planData` (Mixed — the full structured AI output), `status`
(`draft`/`complete`), timestamps. Indexed on `{ userId, createdAt }` for
fast, sorted per-user listing.

## 16. AI generation flow

See the sequence diagram in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).
In short: frontend validates → `POST /api/plans/generate` → backend
validates again → `aiService.js` builds a strict-JSON prompt → calls the
configured provider → parses and normalizes the response (filling safe
defaults for any missing field) → returns `planData` to the frontend
*without saving it* → the user reviews/regenerates → `POST /api/plans`
persists it to MongoDB.

## 17. PDF functionality

`client/src/utils/pdfGenerator.js` uses `jsPDF` to build a real,
multi-page PDF document directly from a plan's data — headings,
paragraphs, and bulleted lists, with automatic text wrapping and
pagination. This is a generated document, not a screenshot of the page.

## 18. Security

Password hashing (bcrypt) · JWT auth · per-resource ownership checks ·
Helmet security headers · CORS restricted to `CLIENT_URL` · rate limiting
(general, auth, and AI-generation tiers) · server-side validation on
every write endpoint · centralized error handler that never leaks stack
traces in production · secrets only ever read from environment variables.

## 19. Testing performed

This project was built and manually verified in an offline sandbox with
outbound network access disabled, so `npm install` / a live `npm run
build` or `npm run dev` could not be executed here. What was verified
instead:

- Every backend `.js` file passed `node --check` (syntax validation).
- Every frontend `.jsx`/`.js` file passed a bracket-balance sanity check
  (no unclosed `(`, `{`, or `[`).
- Manual review of every route against its controller, every controller
  against its model, and every frontend page against the service
  functions it calls, to catch broken imports or mismatched function
  signatures.

**Before you rely on this in production, run it locally and walk
through:** register → login → dashboard loads → create a plan → (with
`AI_API_KEY` set) generate → save → appears in My Plans → view → edit →
duplicate → download PDF → copy → regenerate → delete → logout → confirm
a protected route returns `401` without a token, and that one account
cannot open another account's plan (`403`/`404`).

## 20. Known limitations

- No automated test suite (Jest + Supertest for the backend, React
  Testing Library for the frontend, would be natural additions).
- No email verification or password-reset flow.
- JWT is stored in `localStorage`, not an HTTP-only cookie — see the
  tradeoff note in section 14.
- The Edit Plan page edits the plan's core inputs (title, idea, budget,
  target customers, industry, location, status) rather than every nested
  field inside the generated `planData` — to change the generated content
  itself, use Regenerate.
- No pagination on `GET /api/plans` yet; fine for a personal/college-scale
  number of plans, but would need adding for very large plan counts.
- AI provider errors are surfaced generically to the user (per the "don't
  leak internal errors" requirement) — check the server logs for the
  specific upstream error during debugging.

## 21. Deployment

- **Frontend:** Vercel or Netlify. Build command `npm run build` inside
  `client/`, output directory `dist/`. Set `VITE_API_URL` to your deployed
  backend's URL in the platform's environment variable settings.
- **Backend:** Render, Railway, or any Node host. Root directory
  `server/`, start command `npm start`. Set `MONGODB_URI`, `JWT_SECRET`,
  `AI_API_KEY`, `AI_MODEL`, `AI_PROVIDER`, and `CLIENT_URL` (your deployed
  frontend's URL, for CORS) in the platform's environment variable settings.
- **Database:** MongoDB Atlas — create a cluster, whitelist your backend
  host's IP (or `0.0.0.0/0` if the host uses dynamic IPs), and use the
  provided connection string as `MONGODB_URI`.

No code changes are required to deploy — everything environment-specific
is read from `process.env` / `import.meta.env`, and CORS is already
scoped to `CLIENT_URL`.
